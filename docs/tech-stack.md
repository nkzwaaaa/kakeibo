# Kakeibo 技術スタック設計書

## 1. 目的

Kakeiboで採用する技術と、その選定理由を定義する。

個人開発で実装しやすいことに加え、実務で必要なフロントエンド・バックエンド・DB・テスト・デプロイの知識を習得できる構成を目指す。

## 2. 採用技術一覧

| 分類 | 技術 | 用途 |
|---|---|---|
| 言語 | TypeScript | 型安全な開発 |
| UIライブラリ | React | UI構築 |
| フレームワーク | Next.js App Router | 画面・サーバー処理・API |
| スタイリング | Tailwind CSS | CSSの効率的な記述 |
| DB | PostgreSQL | データ保存 |
| ORM | Prisma | DB操作・スキーマ管理 |
| 認証 | Auth.jsを候補とする | セッション・認証処理 |
| バリデーション | Zod | 入力値の検証 |
| フォーム | React Hook Formを候補とする | フォーム状態管理 |
| テスト | Vitest、Testing Library | 単体・コンポーネントテスト |
| E2Eテスト | Playwright | ユーザー操作のテスト |
| 静的解析 | ESLint | コード品質チェック |
| フォーマット | Prettierを候補とする | コード整形 |
| バージョン管理 | Git / GitHub | ソース・Issue・設計書管理 |
| デプロイ | Vercelを候補とする | Next.jsアプリの公開 |
| DBホスティング | PostgreSQL対応サービス | 本番DB |

※候補と記載した技術は、実装開始時にバージョン・設定・採用有無を確定する。

## 3. 技術選定の理由

### 3.1 TypeScript

**採用理由**

- データ構造を型で表現できる
- 実装時のミスを早い段階で検出しやすい
- ReactのコンポーネントやAPIの型を統一できる
- 実務での型設計・保守性を学べる

### 3.2 React

**採用理由**

- UIをコンポーネント単位で構築できる
- フォームやダッシュボードの状態管理を学べる
- 既存のフロントエンド経験を深められる

状態管理は、まずReact標準のStateや必要に応じたContextを利用する。グローバル状態管理ライブラリは、必要性が明確になってから検討する。

### 3.3 Next.js App Router

**採用理由**

- Reactを用いた画面開発を一貫して行える
- Server ComponentsとClient Componentsを使い分けられる
- Route HandlersでAPIを実装できる
- デプロイまでの流れを経験できる

新規ポートフォリオでは、学習・保守のしやすさを考慮し、採用時点でサポートされている安定版を選ぶ。Next.js 12のPages Routerをそのまま前提にせず、App Routerを基本とする。

### 3.4 Tailwind CSS

**採用理由**

- UIのスタイルを素早く調整できる
- レスポンシブデザインを実装しやすい
- クラス名からスタイルを把握しやすい
- デザインシステムを小さく始められる

複雑なスタイルは必要に応じてCSS Modulesなどに分離する。

### 3.5 PostgreSQL

**採用理由**

- ユーザー、カテゴリ、支出、収入の関係を表現しやすい
- 集計クエリを実装できる
- トランザクションや制約によってデータ整合性を保てる
- 実務に近いRDB設計を学べる

### 3.6 Prisma

**採用理由**

- TypeScriptと組み合わせてDBを操作できる
- スキーマをコードとして管理できる
- マイグレーションを履歴として残せる
- テーブルとリレーションの理解を深められる

Prismaのメジャーバージョンにより設定方法が異なるため、選択したバージョンの公式ドキュメントに合わせる。

### 3.7 認証方式

認証にはAuth.jsを候補とする。ただし、Auth.jsのバージョン、Credentials認証の採用、パスワードハッシュの管理、ユーザー登録処理は別々に検討する必要がある。

方針：

- 認証・セッション管理はライブラリの仕様に従う
- ユーザー登録は必要な場合に独自の処理を実装する
- パスワードを平文で保存しない
- データの所有者確認はAPI・サーバー側で実施する
- クライアント側の画面制御だけで認可を完結させない

認証の具体的な実装方法は、使用バージョンを確定してから決定する。

### 3.8 Zod

**採用理由**

- 入力データの検証ルールをスキーマとして定義できる
- TypeScriptの型とバリデーションを連携できる
- クライアント・サーバー間でルールを再利用しやすい

ただし、クライアント側で検証していても、サーバー側の検証は必ず実施する。

### 3.9 テスト

| 技術 | 主な用途 |
|---|---|
| Vitest | 関数・業務ロジックの単体テスト |
| Testing Library | UIコンポーネントのテスト |
| Playwright | ログインから支出登録までのE2Eテスト |

最初からすべてを網羅するのではなく、金額計算・バリデーション・認証・所有権チェックなど重要な処理からテストする。

## 4. アーキテクチャ方針

- UIはReactコンポーネントで構築する
- サーバー側の処理はRoute HandlersやServer Componentsを用途に応じて使う
- DBアクセスはサーバー側に限定する
- 入力値の検証をUIとサーバーの両方で行う
- 認証とデータの所有権チェックをサーバー側で実施する
- 業務ロジックをUIコンポーネントに過剰に詰め込まない

## 5. 開発環境

- Node.js：採用するNext.jsの要件に適合するLTS版
- パッケージマネージャー：npm
- DB：PostgreSQL（ローカルではDocker Composeを利用）
- エディタ：VS Code
- バージョン管理：Git
- リモートリポジトリ：GitHub

## 6. 品質管理

最低限、以下を実行できるようにする。

```bash
npm run lint
npm run build
npm run test
```

`test` スクリプトはテスト環境の導入後に設定する。

必要に応じて型チェック用のスクリプトも追加する。

```bash
npx tsc --noEmit
```

## 7. デプロイ方針

- アプリケーションはVercelを候補とする
- PostgreSQLは本番利用に適したホスティングサービスを選ぶ
- 開発環境と本番環境の環境変数を分離する
- DBマイグレーションの適用方法を明確にする
- 本番DBの接続情報をGitHubに公開しない
- GitHub Actionsで品質チェックを自動化する
