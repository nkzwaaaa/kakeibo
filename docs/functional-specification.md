## 2. サービス概要

### 2.1 サービスの目的

Kakeiboは、日々の収入・支出を簡単に記録し、月間収支や支出傾向を把握するための家計簿Webアプリケーションである。

### 2.2 設計方針

- 入力の手間を最小限にする
- スマートフォンでも簡単に操作できる
- 家計の状況を直感的に把握できる
- ユーザーごとにデータを分離する
- 認証・認可を適切に実装する
- 機能ごとに責務を分け、保守しやすい設計にする

### 2.3 対象ユーザー

20〜30代の一人暮らしの会社員を主な対象とする。

# 4. 認証機能

## F-01 ユーザー登録

### 概要

新しいユーザーがKakeiboを利用するためのアカウントを作成する。

### 画面

`/register`

### 入力項目

| 項目 | 必須 | 仕様 |
|---|---|---|
| メールアドレス | 必須 | メールアドレス形式 |
| パスワード | 必須 | サーバー側のパスワードポリシーを満たすこと |
| パスワード確認 | 必須 | パスワードと一致すること |

### 処理

1. ユーザーが必要な情報を入力する。
2. 入力値を検証する。
3. 同一メールアドレスの登録状況を確認する。
4. パスワードを安全な方式でハッシュ化する。
5. ユーザー情報をDBに保存する。
6. 成功結果を画面に返す。

### エラー条件

- メールアドレスが未入力
- メールアドレス形式が不正
- パスワードがポリシーを満たさない
- パスワード確認が一致しない
- メールアドレスが既に登録されている
- サーバーエラーが発生した

### 完了条件

- 正常な情報で登録できる
- 不正な入力を拒否できる
- パスワードを平文で保存しない
- 登録後にログインできる

---

## F-02 ログイン

### 概要

登録済みユーザーがログインする。

### 画面

`/login`

### 入力項目

| 項目 | 必須 |
|---|---|
| メールアドレス | 必須 |
| パスワード | 必須 |

### 処理

1. ユーザーが認証情報を入力する。
2. Auth.jsを通じて認証処理を行う。
3. 認証情報を検証する。
4. 認証成功時にセッションを確立する。
5. ダッシュボードへ遷移する。

### エラー条件

- 認証情報が不正
- 入力が不足している
- 認証処理に失敗した

### 完了条件

- 正しい認証情報でログインできる
- 誤った認証情報ではログインできない
- ログイン状態を維持できる
- エラーメッセージに機密情報を含めない

---

## F-03 ログアウト

### 概要

ログイン中のユーザーがログアウトする。

### 処理

1. ユーザーがログアウト操作を行う。
2. Auth.jsでセッションを終了する。
3. ログイン画面へ遷移する。

### 完了条件

- ログアウトできる
- セッションが無効になる
- 認証が必要な画面やAPIを引き続き利用できない

---

## F-04 認証・認可

### 概要

ログイン状態を確認し、ユーザー自身のデータだけを操作できるようにする。

### 仕様

- 認証が必要な画面ではログイン状態を確認する。
- 保護対象APIでもサーバー側の認証確認を行う。
- データ取得・更新・削除時には所有者を確認する。
- クライアントから送信された `userId` を信用しない。
- ユーザーIDは認証済みセッションなどの信頼できるサーバー側情報から取得する。

### 完了条件

- 未認証ユーザーは保護対象APIを利用できない
- 他ユーザーのデータを取得・更新・削除できない
- 認可エラーを適切に処理できる

# 5. 支出機能

## F-06 支出登録

### 概要

ユーザーが支出を登録する。

### 画面

`/expenses/new`

### 入力項目

| 項目 | 必須 | 仕様 |
|---|---|---|
| 金額 | 必須 | 1円以上の整数 |
| カテゴリ | 必須 | 利用可能な支出カテゴリから選択 |
| 日付 | 必須 | 初期値は当日 |
| メモ | 任意 | 設定した文字数上限以内 |

### API

`POST /api/expenses`

### 処理

1. 入力値を検証する。
2. カテゴリが利用可能なものであることを確認する。
3. 認証済みユーザーを特定する。
4. 支出データをDBに登録する。
5. 登録結果を返す。
6. 画面に成功メッセージを表示する。
7. 支出一覧へ遷移する。

### エラー条件

- 金額が未入力
- 金額が0以下
- 金額が整数ではない
- カテゴリが未選択
- カテゴリが存在しない、または利用権限がない
- 日付が不正
- メモが文字数上限を超過
- 未認証
- DB登録に失敗

### 完了条件

- 正常な支出を登録できる
- 不正な入力を拒否できる
- 登録中に二重送信を防止できる
- 成功・失敗がユーザーに分かる

---

## F-07 支出一覧

### 概要

ログインユーザーの支出履歴を一覧表示する。

### 画面

`/expenses`

### 表示項目

| 項目 | 内容 |
|---|---|
| 日付 | 支出日 |
| カテゴリ | 支出カテゴリ名 |
| 金額 | 支出金額 |
| メモ | 登録したメモ |

### API

`GET /api/expenses`

### 仕様

- 自分の支出のみ表示する。
- 日付の降順を基本とする。
- データがない場合は空状態を表示する。
- データが多い場合に備えてページネーションを検討する。

### 完了条件

- 支出一覧を表示できる
- 日付順に表示される
- 空状態を表示できる
- ローディングとエラーを表示できる
- 他ユーザーのデータを取得しない

## F-09 支出編集

### 概要

登録済みの支出を編集する。

### 画面

`/expenses/:id/edit`

### API

`PATCH /api/expenses/:id`

### 仕様

- 既存データをフォームに初期表示する。
- 登録時と同じバリデーションを行う。
- 対象データの所有者をサーバー側で確認する。
- 更新後に詳細画面または一覧画面へ遷移する。

### 完了条件

- 支出を編集できる
- 編集内容がDBに反映される
- 不正な入力を拒否できる
- 他ユーザーの支出を編集できない

## F-10 支出削除

### 概要

登録済みの支出を削除する。

### API

`DELETE /api/expenses/:id`

### 仕様

- 削除前に確認ダイアログを表示する。
- サーバー側で対象データの所有者を確認する。
- 削除成功後は一覧に反映する。

### 完了条件

- 支出を削除できる
- キャンセル時は削除しない
- 他ユーザーの支出を削除できない
- 削除後の画面表示が正しい

## F-17 月間収支集計

### 概要

指定した月の収入・支出・収支を集計する。

### API

`GET /api/dashboard?yearMonth=YYYY-MM`

### レスポンス例

```json
{
  "yearMonth": "2026-10",
  "totalIncome": 300000,
  "totalExpense": 180000,
  "balance": 120000
}
```

### 集計ルール

- 指定月の収入を合計する。
- 指定月の支出を合計する。
- 収支は `totalIncome - totalExpense` とする。
- 集計対象は認証済みユーザー自身のデータとする。
- データがない場合は合計を0とする。

### 完了条件

- 指定月の値を取得できる
- 月をまたいだデータが混入しない
- 収支計算が正しい
- 不正な年月を拒否できる

---

## F-18 カテゴリ別支出集計

### 完了条件

- カテゴリ別の金額を取得できる
- 集計合計が月間支出合計と一致する
- 他ユーザーのデータを含まない

# 9. 入力・画面状態管理

## F-20 入力バリデーション

### 概要

ユーザーが入力したデータを検証し、不正なデータの登録を防ぐ。

### 基本ルール

- 必須項目を確認する。
- 金額は1円以上の整数とする。
- 日付形式を確認する。
- カテゴリの存在と利用権限を確認する。
- 文字列の長さを確認する。
- サーバー側でも同様に検証する。

### 完了条件

- クライアント側で入力エラーを表示できる
- サーバー側でも不正な入力を拒否できる
- クライアント側の検証だけに依存しない

---

## F-21 ローディング・エラー表示

### 概要

通信中や処理失敗時の状態を分かりやすく表示する。

### ローディング

- API通信中はローディング表示を行う。
- 登録ボタンなどは必要に応じて無効化する。
- 同じ操作の二重送信を防止する。

### エラー

- 入力エラーは該当項目の近くに表示する。
- 通信エラーは再試行可能なメッセージを表示する。
- 認証切れの場合はログインを促す。
- 内部情報や機密情報を画面に表示しない。

### 完了条件

- 通信状態をユーザーが把握できる
- エラー発生時に画面が不自然な状態にならない
- エラーから適切に復帰できる

# 11. 共通API仕様

## 11.1 エラー形式

APIエラーは共通形式で返す。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります。",
    "details": [
      {
        "field": "amount",
        "message": "1円以上の金額を入力してください。"
      }
    ]
  }
}
```

## 11.2 HTTPステータスコード

| コード | 用途 |
|---|---|
| 200 | 正常終了 |
| 201 | 新規作成成功 |
| 204 | 削除成功など、返却データがない場合 |
| 400 | 入力値不正 |
| 401 | 未認証 |
| 403 | 操作権限がない |
| 404 | 対象データが存在しない |
| 409 | 重複などの競合 |
| 500 | サーバー内部エラー |

実際のAPIでは、対象リソースの存在を他ユーザーに漏らさないため、認可失敗時に404を返す設計も選択肢とする。

---

# 12. セキュリティ要件

- パスワードを平文で保存しない。
- 認証はAuth.jsなどの認証ライブラリを利用して実装する。
- セッション情報を適切に保護する。
- API側で認証・認可を確認する。
- `userId`をクライアントから受け取って信用しない。
- DB操作時はユーザー所有権を確認する。
- 入力値をサーバー側で検証する。
- 秘密情報をソースコードに含めない。
- 環境変数や秘密情報をGitHubに公開しない。
- エラー応答にパスワード、トークン、SQL情報などを含めない。

# 13. 非機能要件

## 13.1 ユーザビリティ

- スマートフォンで利用しやすいこと。
- 支出登録時の入力負担を抑えること。
- エラーの原因が分かること。
- 登録結果が明確であること。

## 13.2 保守性

- TypeScriptを使用する。
- 機能ごとに責務を分ける。
- 共通UIを再利用する。
- APIとDB操作を適切に分離する。
- 主要なロジックをテストする。

## 13.3 セキュリティ

- 認証済みユーザーだけが保護対象機能を利用できる。
- ユーザーごとにデータを分離する。
- 入力値を検証する。
- 秘密情報を適切に管理する。
